# Apple PIM verified-reply boundary

The integration takes an exact Mail.app account ID, sender address, mailbox and
operator-owned trusted-senders policy. Account discovery must match the unique
enabled account and address. Every message read and authentication check carries
the same account ID, mailbox and RFC message ID. Display names never identify a
participant.

`ApplePIMReplies` requires an evaluated `verified` verdict, the enrolled sender's
expected DKIM signer, and a `messageBinding` generated by the native authentication
checker. The binding contains message/account/mailbox/sender identity and SHA-256
hashes of content, headers and the policy file. The integration rereads the message,
account and policy before returning `VerifiedReply`. Good Company's existing roster,
ownership, remit and replay checks then apply. Only an opaque identity reference is
retained in its ledger.

Commands are exact standalone `STOP`, `DECLINE <assignment-id>` or
`COMPLETE <assignment-id>`. Quoted conversations, additional instructions and
signatures are rejected. The native client exposes only scoped reads; it cannot
send mail, mutate calendars or select a caller-supplied profile/config directory.

## Completion boundary

The installed Apple PIM auth checker supplies a verdict but currently omits the
messageBinding object. This version is refused: a verdict for an unbound lookup
must not authorize another message's command. The required native binding contract
is documented above for an upstream implementation. Genuine and spoofed participant
messages must then traverse this exact path in an authorized test mailbox.

The tests use explicitly fictional native responses and exercise domain mutations,
replay, actor ownership, content/policy/account mismatch and read races. They are
integration regressions, not evidence of a live participant or real mailbox.
Issue #29 remains open for native binding and same-path live acceptance.
